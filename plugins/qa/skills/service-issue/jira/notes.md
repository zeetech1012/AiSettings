## Учётные данные

- `JIRA_URL` — `https://jira.example.com`
- `JIRA_PERSONAL_TOKEN` — PAT (DC-режим; `username/token` — только Cloud)

Инструменты `mcp__jira__*` **deferred** — грузить одним пакетом:
`ToolSearch("select:mcp__jira__jira_create_issue,mcp__jira__jira_update_issue,mcp__jira__jira_transition_issue,mcp__jira__jira_get_transitions,mcp__jira__jira_add_comment,mcp__jira__jira_edit_comment,mcp__jira__jira_search")`

`reporter` в этом инстансе помечен **required** и подставляется владельцем токена автоматически —
задавать не нужно, но и переопределить нельзя (тикет всегда от учётки токена).

## Ловушка 1 — коллизия имён типов задач

`jira_create_issue` резолвит `issue_type` **по имени**, а в русской локали имена дублируются:
встроенный `Task` (глобальный id 3) тоже называется «Задача», встроенный `Bug` (id 1) — «Ошибка».
MCP находит глобальный id, которого нет в схеме типов проекта → Jira отвечает
**«Выбранный тип запроса недействителен»** (в этой локали issue переведён как «запрос», так что
речь про issue type, а не про JSM Request Type). Передать id в `issue_type` тоже нельзя — MCP
отвечает `issue type is required`.

**Рабочий рецепт (один вызов):** в `issue_type` передать уникальное по имени значение
(`"История"` или `"Epic"` — только Jira Software, коллизии нет), а целевой тип задать **сырым id в
`additional_fields`** — он перебивает резолвинг по имени:

```
jira_create_issue(
  project_key="WH", summary="…", issue_type="История",
  additional_fields='{"issuetype": {"id": "10103"}, "epicKey": "WH-1", "priority": {"name": "Low"}}'
)
```

Если тип забыли — доводится потом через `jira_update_issue(fields={"issuetype": {"id": "…"}})`
(`update` тоже принимает сырой JSON и по имени не резолвит).

Типы проектов `API` и `WH` (одна схема, проверено 2026-07-28):

| Тип | id | Когда |
|---|---|---|
| `Epic` | 10000 | инициатива с подзадачами; **требует `customfield_10105` (Epic Name)** |
| `История` | 10100 | техническое имя-заглушка для создания (см. рецепт) |
| `Задача` | 10101 | рабочая единица — **дефолт** |
| `Подзадача` | 10102 | subtask, требует parent |
| `Ошибка` | 10103 | дефект |

## Ловушка 2 — конвертер разметки портит текст

mcp-atlassian конвертирует **markdown → Jira wiki** на записи и **обратно** на чтении. Перегон
лоссовый в обе стороны. Замеры на живых тикетах (2026-07-28):

| Вход | Что стало | Причина |
|---|---|---|
| `KMP + Compose` (несколько `+` в тексте) | `KMP  Compose` — **плюсы съедены** | в wiki `+текст+` = подчёркивание, плюсы схлопываются **парами**; одиночный `+` выживает |
| `models/<svc>.py` | `models/[svc].py` | угловые скобки → квадратные, **даже внутри `{{…}}` и `{code}`** |
| `# комментарий` внутри `{code}` | `h1. комментарий` | решётка в начале строки = заголовок даже в код-блоке |
| `* *жирный* — текст` (жирный в пункте списка) | `- **жирный*` | маркер списка и жирный схлопываются |
| `[MR !16|url]` | `[MR ![](16)…` — ссылка развалена | `!NN` в метке = макрос изображения |
| `[текст\|https://…/merge_requests/18]` | подчёркивание в URL → `\\*`, ссылка битая | экранирование `_` внутри URL |
| `{{ui.viewModel.*Tariff*}}` | `{{ui.viewModel._Tariff_}}` | астериски в glob → подчёркивания |
| `{{code.all { it == null }}}` | обрезано на первой `}` | фигурные скобки схлопываются с закрывающими `}}` |
| `**жирный**` | `\*\*жирный\*\*` | двойное экранирование |
| `---` (разделитель) | пустой `h2.` | markdown-hr → заголовок |
| `- [x] пункт` (чекбокс) | ломается | markdown-чекбоксы не поддержаны |

**Правила записи, выведенные из этих замеров:**

- Писать **сразу в Jira wiki-разметке**: `h2.`/`h3.` заголовки, `*` пункты (`**` вложенные),
  `{{моноширинный}}`, `{code}…{code}`, `{quote}…{quote}`, `||заголовок||` для таблиц.
- Идентификаторы с `_` и любые `+` — **в `{{…}}`**. Внутри монospace `_` и `+` выживают.
- **Фигурные скобки** в коде — только в блочном `{code}`, не в `{{…}}`.
- **Решётку** в начале строки внутри `{code}` сдвигать отступом (`  # comment`) — тогда остаётся литералом.
- **Угловые скобки** не спасти ничем: заменять на заглавные плейсхолдеры (`<JWT>` → `JWT`) и писать
  примечание переноса.
- **Жирный не использовать внутри пунктов списка** — только в отдельном абзаце.
- **URL с `_`** не заворачивать в ссылку — выносить в `{code}`-блок голым текстом.
- **`!NN`** (номера MR) — только в `{{…}}`, никогда в метке ссылки.
- **Glob-паттерны** и команды прогона — в блочный `{code}`, не в `{{…}}`.
- **Не использовать** `---`, `**жирный**`, markdown-чекбоксы, markdown-таблицы.
- В `summary` **не экранировать** `&` — попадёт литеральным `&amp;`.
- Прочитанное через `jira_get_issue`/`jira_transition_issue` описание — **не источник истины**:
  ответ переконвертирован и выглядит хуже, чем хранится. `expand=renderedFields` не помогает.
- **Проверять результат глазами в UI** (`https://jira.example.com/browse/<KEY>`). Для больших объёмов
  технического текста надёжнее REST `PUT /rest/api/2/issue/<KEY>` с PAT из файла (права 600) —
  байт-в-байт, без конвертации.

## Ловушка 3 — статус только через transition

`jira_create_issue` статус не принимает: тикет всегда рождается во входном статусе (`Backlog`).
Целевой статус — вторым вызовом `jira_transition_issue`. **Проверять после прогона JQL-запросом:**
при пакетной работе легко создать партию и уйти дальше, не проставив статусы (случилось на
`WH-14`…`WH-17`, поймано только сверкой `project = WH ORDER BY key`).

## Ограничения инстанса

- **Вложения не загружаются.** У MCP есть только `jira_download_attachments`. Поле `Вложение`
  в схеме создания присутствует, но инструмента записи нет → файлы переносить вручную либо через
  REST `POST /rest/api/2/issue/<KEY>/attachments`.
- **`duedate` недоступен на экране создания** — Jira отвечает `Field 'duedate' cannot be set`.
  Срок писать в текст описания.
- **Пользователей всего 4**: `ppodsevalnikov`, `svetlichny`, `vvasilev`, `imanevich`. Любой другой
  исполнитель не назначается — писать его строкой в описание.
- **Приоритеты**: `Highest`, `High`, `Medium`, `Low` (проверены в бою).
- **Архитектуры прав нет**: ключевые права на холдере `applicationRole` = любой залицензированный
  сотрудник видит всё. Restricted-контура нет, issue security schemes = 0. Не заводить сюда то,
  что должно быть ограничено по доступу, пока не выполнены шаги настройки схем.
- `jira_batch_create_issues` с `validate_only=true` — **бесполезен**: возвращает успех на заведомо
  неверные типы. Не использовать как проверку.

## Алгоритм — создание одного тикета

1. **Дедуп.** `jira_search` по JQL (`project = X AND summary ~ "…"`); похоже на существующий —
   вернуть его, не создавать вслепую.
2. **Собрать тело** в wiki-разметке по шаблонам из вики (`task-spec-templates`, «Правила
   баг-репорта»). Обязательный минимум: задача или доработка — критерий приёмки; баг —
   Actual/Expected плюс Steps. Нет минимума — вернуть на доуточнение, **не создавать**.
3. **Создать** одним вызовом: `issue_type="История"` плюс целевой `issuetype.id`, `priority`,
   `epicKey` в `additional_fields`; `assignee` отдельным параметром.
4. **Статус** `jira_transition_issue(issue_key, transition_id)` — если целевой не входной.
5. **Вернуть** ключ и `https://jira.example.com/browse/<KEY>`, попросить сверить рендер описания.

## Алгоритм — перенос из Huly

Huly (huly MCP) — только чтение; оригиналы не трогать, перенос = копия.

**Что huly MCP не отдаёт** (проверено): `get_issue` не возвращает ни **автора**, ни **тип задачи**.
`list_issues` фильтрует по `assignee`, но **не по автору**. `list_activity` даёт автора непрозрачным
числовым social-id (`1175027443461586945`), а `get_person` его не резолвит — id-пространства разные,
и у одной учётки бывает несколько social-id. ⇒ Фильтр «где я автор» построить нельзя; авторство
комментариев не восстанавливается. Отбор — по `assignee` плюс подпись в тексте
(`descriptionSearch` по `Severity`, `Root cause`, `Критерий приёмки`, `repro`), список согласовывать.

**Маппинг проектов:** `API` → `API`, `HOME` («[hw+sw] Example HOME») → `WH`.

**Маппинг типов** (тип в Huly недоступен ⇒ вывод из статуса и заголовка):

| Признак | Jira |
|---|---|
| статус `ЗАПРОС НА ИЗМЕНЕНИЕ`, либо есть подзадачи | `Epic` 10000 |
| статус `ИСПРАВЛЕН`; заголовок с «Баг:», «БЛОКЕР:», «Краш», «Не работает», «Невозможно» | `Ошибка` 10103 |
| остальное | `Задача` 10101 |

Эвристика неточная — часть дефектов с нейтральным заголовком уедет как `Задача`. Нужна вычитка.

**Маппинг статусов:**

| Huly | Jira | transition |
|---|---|---|
| `БЭКЛОГ` | Backlog | входной, transition не нужен |
| `ЗАПРОС НА ИЗМЕНЕНИЕ` | Список задач | 11 |
| `ПЛАН (Уточнение сроков)` | Selected for Development | 21 |
| `В РАЗРАБОТКЕ` | В работе | 31 |
| `В ТЕСТИРОВАНИИ`, `ПРОТЕСТИРОВАНО (Verified)` | В тестировании | 51 |
| `ИСПРАВЛЕН`, `СДЕЛАНО` | Выполнено | 41 |
| `ОТМЕНЕНО` | аналога нет — **не переносить** (решение 2026-07-28) | — |

**Маппинг приоритетов:** `urgent`→Highest, `high`→High, `medium`→Medium, `low`→Low,
`no-priority`→не задавать.

**Маппинг исполнителей:** `Васильев,Вячеслав`→`vvasilev`, `Светличный,Артур`→`svetlichny`.
Все прочие → assignee пустой плюс строка «Исполнитель в Huly: Фамилия,Имя» в футере.

**Порядок прогона:**

1. Собрать список к переносу, **согласовать с пользователем** до первого создания.
2. Иерархия — в два прохода: сначала родитель (`Epic` с Epic Name), потом дети с
   `additional_fields={"epicKey": "<KEY родителя>"}` (Epic Link = `customfield_10108`).
3. На каждую задачу: `get_issue` плюс `list_comments` → create (тип, приоритет, assignee, epicKey
   одним вызовом) → transition → `jira_add_comment` на каждый комментарий.
4. **Даты конвертировать через `date -u -r`**, не считать в голове. `subIssues` в huly врёт
   (показывало 20 при фактических 24) — состав детей брать запросом `parentIssue`.
5. В футер описания — провенанс: исходный идентификатор, дата создания, статус на момент переноса,
   исполнитель в Huly, оценка, родитель. Без выдуманных URL.
6. **Пилот сначала:** 1–2 задачи, показать пользователю, получить подтверждение рендера. Учесть,
   что пилот не поймает всё — режимы порчи зависят от содержимого (плюсы, код-блоки, ссылки).
7. **Финальная сверка JQL** по всему проекту: типы, статусы, Epic Link.
8. Доска Huly меняется во время прогона (статусы и исполнители переставляют) — читать состояние
   на момент переноса и так и подписывать в футере.
