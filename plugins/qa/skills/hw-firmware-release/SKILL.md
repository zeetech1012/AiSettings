# SKILL: HW_FIRMWARE_RELEASE

Перед записью проверить местоположение тестов: общий Test Repository и проект релиза могут различаться.
Не использовать исторические ключи тестов из старых релизов; подтвердить актуальный состав чтением Jira.

Выведен из релизов ФОБОС 8.8 и 7.12 (2026-09-23). Общие правила Xray — в глобальном `CLAUDE.md`, раздел «Xray в Jira DC»
и «Нейминг в Xray». Массовые правки полей и шагов — скилл `xray-bulk-edit`.

## Вход

- Каталог сборки от разработчика, например `~/Downloads/x.x.7.12/`: заметки к версии (`.txt`, UTF-8 с CRLF) и файлы
  `ph<модель><версия>_<сборка>.hex|.bin`. Имя кодирует ВПО: `ph13712` → `1.3.7.12`, `ph31612` → `3.1.6.12`.
- Test Plan, который владелец завёл сам (ключ), и исполнитель (username, не отображаемое имя: `example-user`).

## Процедура

1. **Прочитать заметки к версии** и разложить пункты по тестам общего репозитория тестов (например WQA) (`/Испытания изделий/<Продукт>/Тестирование/…`).
   Основание для каждой пары — формулировка пункта и тема теста. Если в задачах релиза есть раздел «Как проверить»,
   тесты берутся оттуда.
2. **В план включать только проверки `[Тестирование]`.** Проверки `[Метрология]`, `[ОТК]`, `[Лаборатория]` живут в своих
   наборах (`[TS] [<Продукт>] [<Исполнитель>] …`), результат прикладывается к плану протоколом исполнителя.
   Обязательную регрессию выбирать из актуального общего репозитория тестов по утверждённому базису.
3. **Заполнить конфиг** по образцу `release.example.json`: версия, план, исполнитель, тесты, прогон, связи.
   Тема прогона — `[TX] [<Продукт>] прогон ВПО <x.x.x.x>: <файл>`.
4. **Сухой прогон:** `python3 scripts/hw_release.py release.json --dry`. Показать владельцу, что будет записано.
5. **Запись** по прямой просьбе владельца: `python3 scripts/hw_release.py release.json` → `ok=N fail=0`.
   Повторный запуск печатает «прогон уже есть» и ничего не пишет.
6. **Статусы задач релиза**, если владелец просит: переход выбирать по имени целевого статуса на каждом шаге
   (`GET …/transitions` → `to.name`), с `?notifyUsers=false`.
7. Записать операцию в `Company/_wiki/qa-infra/log.md` (append-only).

## Ловушки

| Что | Как на самом деле |
|---|---|
| Статус «В тестировании» из «Бэклог» | прямого перехода нет: «Готово к разработке» → «В работе» → «В тестировании» |
| Направление связи `Tests` | `POST /rest/api/2/issueLink {inwardIssue: тест, outwardIssue: задача}` даёт «тест tests задача», у задачи «tested by» |
| Исполнитель Test Run | `PUT /rest/raven/1.0/api/testrun/<id>/assignee?user=<username>`; при создании прогона с исполнителем Xray ставит его и в Test Run |
| id типов Xray | 10200 Test · 10201 Test Set · 10202 Test Execution · 10203 Pre-Condition · 10204 Test Plan · 10205 Sub Test Execution |
| Тесты попадут в план «через прогон» | не полагаться: план — объём, забытый тест в нём висит TODO и виден; прогон создавать из плана |
| Результаты из журнала испытаний (`~/Documents/Анализ.xlsx`) | переносить генератором `qa-infra/xray/build_retro_runs.py`; сеансы без даты не переносятся, дату не выдумывать |
| История задним числом | Xray берёт последний **созданный** прогон, а не по дате: импорт истории после прогона версии перекроет его статусы |
| Test Version в прогоне | это версия шагов теста (`testVersion: v1`), не поле задачи Test; новая версия заводится, когда шаги меняются между прошивками |

## Границы

- Test-задачи и наборы здесь не создаются; прогон, версия и связи — да.
- Удалять Test Run можно только в статусе TODO; прогон с результатами не удалять.
- Имена сотрудников в описаниях не писать: исполнитель — полем.
