# SKILL: JIRA_VAULT_SYNC

Решения карты `coverage-queue` (vault `Company/_wiki/qa-monorepo/wayfinder/coverage-queue/`): тикет 01 — формат
постановки и место очереди, тикет 05 — этот скрипт. Стоячее правило: **Jira — истина для того, что кто-то будет
делать; vault — планы и постановки.** Поэтому синхронизация односторонняя: из Jira в vault, статус в vault не
правится, запись в Jira отсюда не делается никогда.

## Когда применять

- После заведения, закрытия или переразметки QA-задач на доске IOT (`roadmap-qa`, дети QA-эпиков).
- Перед сессией по очереди: свежие `jira_status` в шапках и таблица `tasks/README.md`.
- После того как в постановке появилось тело (критерии `АС-n`): колонка «Тело» пересчитывается.

Одиночную правку шапки руками не делать — следующий запуск скрипта её всё равно перепишет.

## Что скрипт пишет и чего не трогает

| Пишет (машинная часть шапки) | Не трогает (человеческая часть) |
|---|---|
| `jira`, `summary`, `jira_status`, `epic`, `labels`, `component`, `conditions`, `synced` | `type`, `project`, `status` (жизненный цикл заметки), `executor`, `needs`, любые другие ключи, **тело целиком** |
| файл `tasks/IOT-<n>.md` для задачи выборки без постановки — скелет шести разделов канона, тело пустое | существующие файлы других форматов (`contours-prod-staging-test.md`), `cond-*.md` — читаются только для индекса |
| таблица между `<!-- queue:begin -->` и `<!-- queue:end -->` в `tasks/README.md`, поле `updated:` README | текст README вне маркеров |

Постановка для задачи, закрытой в Jira, **не удаляется и не архивируется**: обновляется `jira_status`, строка уходит
в конец таблицы. Судьба таких постановок (`status: done`, архив) — туман карты, решение владельца; до него скрипт
поле `status` не касается.

## Откуда данные

- **Выборка** — `config/queue.json`: JQL `project = IOT AND issuetype in (Задача, История) AND statusCategory != Done
  AND (labels = roadmap-qa OR "Epic Link" in (<QA-эпики>))`, минус `exclude` (задачи разработки в QA-эпиках, каждая с
  причиной). Ключи существующих постановок вне выборки (закрытые, переразмеченные) дочитываются поштучно.
- **Условия задачи** — `data/conditions-by-task.tsv`: ключ → перечень `<план>-<id>` или селектор
  `area:<план>:<префикс области>`; значения проверяются по вендоренному реестру условий qa-monorepo
  (`src/main/resources/coverage/conditions-<дата>.json`, путь в конфиге). Задача без строки → `conditions: []`.
  Ключ, которого нет ни в выборке, ни в vault, печатается отдельно — соответствие устарело.
- **Индекс**: «Тело» = `да`, если в теле есть хотя бы один критерий `АС-n`; `needs` — из человеческой части шапки.

## Три обязательных свойства

| Свойство | Как реализовано |
|---|---|
| сухой прогон `--dry` | печатает JQL, выборку, исключения, `+ создать` / `~ обновить` с перечнем полей, без записи |
| защита от повторного применения | шапка сравнивается по полям без `synced`; равна — файл не пишется, `synced` не меняется; таблица сравнивается текстом; повторный запуск печатает «изменений нет» |
| проверка результата чтением | после записи папка перечитывается через `app.vault.read`, каждая шапка сверяется по полям и `synced`, тело — на неизменность, таблица — на совпадение; итог `ok=N fail=0` |

## Команды

```
python3 ~/.claude/skills/jira-vault-sync/scripts/jira_vault_sync.py --dry      # дельта, ничего не пишется
python3 ~/.claude/skills/jira-vault-sync/scripts/jira_vault_sync.py            # запись + проверка чтением
python3 ~/.claude/skills/jira-vault-sync/scripts/jira_vault_sync.py --verify   # только сверка, код 1 при расхождении
```

Требования: Obsidian запущен (`open -a Obsidian`, готовность по `obsidian vault list`), PAT в `~/jira_pat` или
`JIRA_PERSONAL_TOKEN`, реестр условий по пути из конфига (иначе `--registry <путь>`). Только stdlib.

**Запись запускает владелец через `!`.** Сухой прогон (`--dry`) и `--verify` агент выполняет сам; запуск без флагов
из сессии агента классификатор харнесса отклонил 2026-09-22 с причиной «Instruction Poisoning» — скрипт переносит текст
из внешней системы (Jira) в заметки. Порядок: агент показывает вывод сухого прогона, владелец запускает запись, агент
после этого выполняет `--verify` и фиксирует итог в vault и журнале.

## Ловушки, проверенные 2026-09-22

- **`obsidian eval` с `await` на верхнем уровне** ничего не выполняет; код обёрнут в async IIFE, итог приходит файлом
  (`.tmp` → `rename`), скрипт опрашивает файл. CLI иногда не отдаёт управление — таймаут `subprocess` штатный.
- **`app.metadataCache` отстаёт от записи** — для сверки читается сырой текст `app.vault.read`, frontmatter разбирается
  своим парсером (плоские ключи, `"…"`, flow-списки `[a, b]`, блок-списки `- x`, комментарии `# …` после значения).
- **Замена шапки — точным совпадением старого блока** (`split(old).length - 1 === 1`), иначе отказ: якорь, совпавший
  дважды или ни разу, уже портил заметки в этой линии работы.
- **`String.replace` со строкой-шаблоном** трактует `$` в замене — используется функция-заменитель.
- **Пакетный поиск Jira `key in (…)` с набором полей** уходит в таймаут — существующие ключи дочитываются по одному,
  сетевой сбой повторяется с нарастающей паузой.
- **Две копии скрипта одновременно не запускать** — исчерпание локальных портов (`OSError: [Errno 49]`) и гонка
  за один README.

## Границы

- Условия без задачи Jira (`cond-<план>-<id>.md`) скрипт **не создаёт** — какие условия получают постановку, решает
  тикет 06 карты; готовые файлы попадают в таблицу.
- В Jira ничего не пишется. Постановка, готовая стать задачей, переносится в Jira по канону `service-issue`.
- Расширение на доски WH и LK — отдельный эффорт, не правка конфига.
