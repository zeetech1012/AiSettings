Тест-архитектура KMP: где что гонять

⏱ ~6 мин · ZPD: продвинутый · Цель урока: одна чёткая ментальная модель — какой source set для какого теста и на каком таргете он исполняется.
Зачем (миссия): карьера/широта — уметь спроектировать тест-стратегию любого KMP-проекта, а не одного. Этот урок даёт каркас, на который дальше навесим инструменты (Kaspresso / XCUITest / Allure).

1. Каркас: тесты живут в source sets, исполняются на targets

В KMP есть два независимых измерения, которые новички путают:

  • Source set — где лежит код теста (commonTest, androidUnitTest, iosTest…).
  • Target — что его компилирует и исполняет (JVM-хост, Android-устройство, iOS-симулятор/Native).

Ключевой факт: commonTest компилируется во ВСЕ объявленные таргеты и гоняется на каждом — это «контртест» к commonMain.[1] Платформенные тесты живут в своих source sets и гоняются только на своём таргете.[4]

// source set → на каком(их) target(ах) исполняется commonTest → JVM-хост + iOS(Native) + … # общая логика, kotlin.test androidUnitTest → JVM-хост # быстро, без устройства (Robolectric/моки) androidInstrumentedTest → Android device/эмулятор # Espresso/Kaspresso, реальный UI iosTest → iOS-симулятор (Native) # compose.uiTest / Native unit jvmTest / desktopTest → JVM-хост # если есть desktop-таргет

2. Три вопроса, выбирающих слой

Чтобы решить, куда положить тест, спроси по порядку:

  1. Это чистая логика (ViewModel/UseCase/mapper/валидация), без платформенных API? → commonTest. Только мультиплатформенные библиотеки (kotlin.test, coroutines-test, Turbine).[1]
  2. Это платформо-специфичное поведение или нужен платформенный рантайм (Android Context, реальный JVM-хост, Native)? → платформенный unit source set (androidUnitTest / iosTest / jvmTest).
  3. Это UI? → зависит от того, shared ли он (Compose Multiplatform) и нужен ли реальный девайс — см. таблицу.

4. Три неочевидные истины

commonTest бежит и на Native. Тот же тест ViewModel исполняется на JVM-хосте И на iOS-симуляторе. Поэтому в commonTest — только мультиплатформенные библиотеки; никакого JVM-only (MockK, Robolectric, java.*).[1]
Compose-UI-тест ≠ unit-тест. runComposeUiTest НЕ использует JUnit TestRule — ты вызываешь функцию и работаешь с ComposeUiTest-receiver'ом; finders/matchers/actions те же, что в Jetpack Compose.[2] Это причина держать compose.uiTest в iosTest/платформенном set'е, а не в commonTest — иначе Compose-runtime утечёт в JVM-host unit (где нет Robolectric). так и сделано в energy-app-native
API эволюционирует — знай актуальное. Compose Multiplatform 1.11 ввёл v2 ComposeUiTest на non-Android таргетах со StandardTestDispatcher по умолчанию (вместо Unconfined → корутины в порядке очереди, стабильнее), а старые runComposeUiTest/runSkikoComposeUiTest задепрекейтил.[5] С 1.9 runComposeUiTest принимает suspend-лямбду (awaitIdle()).

5. Проверь себя feedback loop

Для каждого сценария реши слой/инструмент, потом раскрой ответ.

Q1. Тест: «валидатор телефона отклоняет буквы». Куда?
Ответ
commonTest + kotlin.test. Чистая логика, без платформы → общий слой, гоняется на всех таргетах. Гоняешь обычно на JVM-хосте (быстро).
Q2. Тест: «на shared Compose-форме ввод нечислового ID оставляет кнопку Add disabled». Backend не нужен. Куда?
Ответ
runComposeUiTest в commonTest/iosTest. UI shared (Compose MP), без живого backend → один тест на все платформы, локаторы по testTag/semantics. Не нужен ни Kaspresso, ни XCUITest.
Q3. Хочешь использовать MockK и Robolectric в тесте ViewModel. Можно ли положить его в commonTest?
Ответ
Нет. MockK/Robolectric — JVM-only; commonTest компилируется и под Native → не соберётся. Либо клади в androidUnitTest (JVM-хост), либо пиши ручные fakes (expect/actual) и оставляй в commonTest.
Q4. Тест: «на реальном iPhone системная клавиатура закрывается по тапу вне поля» (HOME-7-подобное). Куда?
Ответ
XCUITest (Swift), iOS-специфика. Системная клавиатура/фокус — это поведение ОС, которое Compose-UI-тест в процессе не ловит; нужен нативный драйвер на устройстве/симуляторе. (Кросс-платформенную UI-логику оставляем в runComposeUiTest.)
Q5. Один и тот же тест ViewModel ты гоняешь и на JVM-хосте, и на iOS-симуляторе. Это баг конфигурации или норма?
Ответ
Норма. commonTest по дизайну компилируется и исполняется на КАЖДОМ объявленном таргете — это бесплатная регрессия-гарантия, что общая логика ведёт себя одинаково на JVM и Native.[1]
