runComposeUiTest vs Kaspresso

⏱ ~7 мин · ZPD: продвинутый · Цель: понять, что это не конкуренты на одном уровне, и по каким осям выбирать. Опора на Урок 1 (слои).
↩ Из Урока 1: UI-тесты — платформенный слой. Здесь увеличиваем именно его.
Зачем (миссия): карьера/широта — на собеседовании частый вопрос «Compose UI test или Kaspresso?». Правильный ответ начинается с «это разные уровни абстракции», а не «Kaspresso лучше».
TL;DR: runComposeUiTest — кросс-платформенный движок Compose-теста (semantics-дерево, изолированно, Android+iOS+desktop). Kaspresso — Android-only instrumented фреймворк (Espresso + UI Automator), который драйвит всё живое приложение (Compose + View + system UI) и добавляет стабильность (flakySafely), robots, логи, скриншоты. Они на разных полках.

1. Разный уровень, а не «А против Б»

runComposeUiTestKaspresso (+compose-support)
Что этодвижок Compose-теста (KMP)Android instrumented фреймворк поверх Espresso + UI Automator[1]
ПлатформыAndroid, iOS, desktop (один тест)только Android
Точка входаrunComposeUiTest { }, receiver ComposeUiTest, без JUnit-rule[2]TestCase/run{} + createAndroidComposeRule<MainActivity>()
Что видиттолько Compose semantics-дерево, что ты задал setContentживой Activity + Compose + View-interop + system UI (нотификации, permission-диалоги, pressBack, другие приложения)
ЛокаторыtestTag/semantics, finders как в Jetpack Composeте же + Kakao-Compose ComposeScreen/KNode page-objects, единый DSL для View и Compose[3]

Тонкость: Kaspresso на Android внутри использует тот же Compose-test API (ComposeTestRule). То есть «движок» один; Kaspresso — оболочка с устройством, system-UI и стабильностью.

2. Главная ось — что нужно достать

Compose-тест достаёт только Compose-дерево. Ты сам собираешь композаблы через setContent { … } (или createComposeRule на Android) — изолированно, без реального Activity/Koin/backend. Идеально для UI-логики экрана: «невалидный ввод гасит кнопку», «поле принимает текст».
Kaspresso достаёт всё приложение и ОС. createAndroidComposeRule<MainActivity>() поднимает реальную Activity (навигация, Koin, реальные экраны), а UI Automator даёт system-UI: permission-диалоги, шторку, pressBack, переключение приложений. Нужно для функц./E2E на устройстве.

3. Изоляция: createComposeRule vs createAndroidComposeRule

Внутри Android-Compose-теста две фабрики:[4]

  • createComposeRule() — без Activity, контент задаёшь сам. Изолированный рендер — быстрый, без backend (как «network-free baseline»).
  • createAndroidComposeRule<A>() — с доступом к Activity. Нюанс: нельзя звать setContent, если Activity уже его вызвала; частый приём — пустая ComponentActivity как хост.

4. Синхронизация — где живёт боль углубление

Compose-тест авто-синхронизируется: перед каждым assert/action ждёт, пока UI-дерево станет idle.[5] waitForIdle() зависит от autoAdvance (по умолчанию true — крутит Compose-clock до idle).

Ловушка never-idle UI. Если экран НИКОГДА не становится idle — живой WebSocket, бесконечная Lottie-анимация — авто-sync (и Espresso idling) ждёт вечно/падает. Симптом: RootViewWithoutFocus, зависший Espresso.pressBack(). Решения:
  • flakySafely(timeoutMs=…) { … } — Kaspresso ретраит блок до таймаута (дефолт 10с), не требуя idle.[1]
  • waitUntil { condition } — ждать конкретное условие вместо общего idle.[6]
  • гнать через UI Automator (device.pressBack()) — он не завязан на Espresso-idle.
// Compose-тест: авто-sync ок на статичном экране
onNodeWithTag("btn_add_device").assertIsNotEnabled()

// Kaspresso: живой экран не idle → flakySafely ретраит
flakySafely(timeoutMs = 15_000) {
    composeTestRule.onNodeWithTag("screen_charger_control").assertIsDisplayed()
}

6. Проверь себя feedback loop

Q1. «runComposeUiTest или Kaspresso — что выбрать?» Что ответить ПЕРВЫМ на собеседовании?
Ответ
«Это разные уровни». runComposeUiTest — кросс-платформенный движок Compose-теста (изолированно, Android+iOS). Kaspresso — Android instrumented фреймворк, драйвит всё приложение + system-UI + стабильность. Выбор зависит от: нужен ли реальный девайс/ОС/backend и нужна ли кросс-платформенность.
Q2. Тест навигации на живом charger-экране падает: Espresso.pressBack() → RootViewWithoutFocus. Почему и чем чинить?
Ответ
Экран never-idle (живой WebSocket/Lottie) → Espresso ждёт idle, которого нет. Чинить: flakySafely / waitUntil / UI Automator device.pressBack() (не завязан на Espresso-idle), а не самим Espresso.pressBack.
Q3. Хочешь один UI-тест формы, который пройдёт и на Android, и на iOS. Kaspresso подойдёт?
Ответ
Нет — Kaspresso только Android. Нужен runComposeUiTest (кросс-платформенный движок). Один код, локаторы по testTag, гоняется на каждом таргете.
Q4. Нужно проверить, что в списке появилась зарядка после реального логина и навигации из живого приложения. Слой?
Ответ
Kaspresso + createAndroidComposeRule<MainActivity>() — нужен живой Activity, навигация, реальный backend. runComposeUiTest/createComposeRule видят только изолированное Compose-дерево, без реального приложения.
Q5. Правда ли, что Kaspresso «не использует» Compose-test API и парсит экран сам?
Ответ
Нет. Kaspresso-compose-support = Kakao-Compose + interceptors поверх того же Compose-test API (semantics-дерево). Движок локации — общий; Kaspresso добавляет DSL, стабильность, system-UI.[3]
