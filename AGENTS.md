# Правила работы AI-агента (командный baseline)

> Правила для Claude Code. Подключаются через `@AGENTS.md`-импорт в `~/.claude/CLAUDE.md`
> либо копипастом из онбординг-гайда. Личные настройки и секреты сюда не попадают.

## Роль агента — заполняется в личном файле, не здесь

Роль определяет, **кем выступает агент**: уровень экспертизы и специализацию, стиль (сразу
к делу / развёрнуто), язык объяснений и кода, что флагировать до реализации (напр. flaky-тесты,
плохая поддерживаемость). Это персональная часть — в командный файл она не вписывается,
иначе копия разойдётся с baseline. Заполняется в `~/.claude/CLAUDE.md` над строкой `@AGENTS.md`
(образец — `claude/CLAUDE.example.md`).

> Всё, что ниже (правила написания кода, качество, дисциплина задач, Оккам, LLM-Wiki, handoff) —
> передаётся **как есть**.

## Дисциплина задач: баг = единица работы

- Нашёл дефект → **один** баг в трекере: root-cause + repro + предлагаемый подход + severity.
  Этого достаточно для разработчика. Тикеты-обёртки («реализовать фикс бага X») не заводить.
- Перед созданием — дедупликация: сверить с открытыми тикетами и wiki-списком багов
  (fulltext-поиск трекера ненадёжен); после transient-ошибки create проверить, не создался ли дубль.
- Прод-код QA не правит (баг → dev), repro остаётся красным до фикса.
- **Трекер задач и планировочный слой разделены.** В трекер попадает то, что кто-то будет *делать*:
  баги, задачи, запросы на изменение. Карты планирования, открытые вопросы и решения, к которым
  команда ещё идёт, живут в вики и на командную доску не выносятся — иначе доска забивается тем,
  что никто не берёт в работу. Планировочная карта ссылается на тикеты трекера, но не заменяет их.

## Роутинг по стекам

| Репозиторий | Стек | Заметки |
|---|---|---|
| `energy-app-native` | Kotlin (KMP + Compose + Kaspresso, L1-L2) + Swift/XCUITest (iOS, L3) + Allure | локаторы — единый `testTag`-контракт |
| `qa-monorepo` | Python: `pytest` + `httpx` + `pydantic` v2 + `allure-pytest` (+ `websocket-client`, `pika`) | backend black-box (API / контракты / E2E); уровень теста — маркер, не каталог |
| `auth_http` и др. Go-сервисы | Go: `net/http`, `httptest`, `testing`/testify | тесты сервиса изнутри |

Default для QA-задачи: бэкенд/контракт → Python (`qa-monorepo`); экран/Compose → Kotlin (KMP);
iOS-специфика (клавиатура, secure-field, permissions) → Swift/XCUITest. Неясно — спроси.
**Проектный instructions-файл репозитория главнее этого файла.**

## Как писать код

1. **Думай до кода.** Проговаривай допущения; несколько трактовок — покажи, не выбирай молча;
   есть путь проще — скажи; неясно — остановись и спроси.
2. **Простота.** Минимум кода под задачу: без спекулятивных фич, абстракций для одноразового
   кода и «конфигурируемости», которую не просили.
3. **Хирургические правки.** Трогай только нужное; не «улучшай» соседний код; стиль файла
   важнее твоих предпочтений; подчищай только мусор, созданный твоими же правками.
4. **Критерий успеха до кода.** «Почини баг» → «тест, воспроизводящий баг, затем зелёный»;
   формулируй проверяемые шаги и итерируй до verified.

## Правила качества (все стеки)

- Один класс/функция = одна ответственность.
- Никаких хардкодов URL / учётных данных / ID — только ENV, фикстуры, `BuildConfig`.
- Никаких sleep-ожиданий (`Thread.sleep` / `delay` / `time.Sleep`) — polling / framework-wait с таймаутом.
- Тесты независимы: без разделяемого мутабельного состояния и порядка выполнения.
- Flaky-тест = сломанный тест; не прятать за retry/xfail.
- Локаторы стабильные (`data-testid`, `testTag`), не XPath/CSS-класс/`R.id`.
- Каждый тест аннотирован для Allure (title/severity + epic/feature/story) и построен
  по Arrange-Act-Assert со steps; вложения (ответы API, скриншоты) — чтобы отчёт читался не-разработчиком.
- **Given-When-Then — текстом внутри шага Allure**, а не через Gherkin: `Given: …` / `When: …` /
  `Then: …` в названии шага. Cucumber и `.feature`-файлы не заводим — источник истины остаётся
  кодом теста, второй артефакт расходится с ним молча. Gherkin уместен только там, где автотеста
  не будет: ручные сценарии приёмки в системе тест-менеджмента.

## Чеклист ревью — флагируй автоматически

- sleep-ожидание → flaky-риск; хардкод URL/кредов → env-violation; нет Allure-аннотаций →
  reporting gap; XPath/CSS-локатор → fragile selector; фикстура с неверным scope → isolation risk;
  общее мутабельное состояние → order dependency; несколько логических assert без steps →
  debugging nightmare.
- При диагностике (flaky / красный тест / триаж) — принцип Оккама: простейшее объяснение,
  бьющееся с фактами, проверяй первым (skill `occams-razor`).

## Документация сервисов

- Источник истины по эндпоинтам/моделям — контекст-док сервиса (`docs/<service>.md`,
  генерируется skill'ом `service-doc` в репозитории сервиса).
- Дока отсутствует → **не угадывать** эндпоинты, поля и структуры ответов. Остановись
  и запроси контекст-док.

## Тестовая документация — минимальный набор по ISO/IEC/IEEE 29119-3 (словарь ISTQB)

Документы тестирования называем и структурируем по стандарту, а не по наитию. Ведём **четыре** типа,
остальные типы стандарта не заводим, пока в них нет реальной нужды.

| Тип по 29119-3 | Что это на практике | Где живёт |
|---|---|---|
| **Test Plan** | объём, подход, уровни, критерии входа и выхода, риски, окружение, раздел «что не тестируем и почему» | export-слой вики → корпоративная вики |
| **Test Environment Requirements** | контуры, доступы, ключи, гейты небезопасных операций, изолированный стенд | раздел плана |
| **Test Status / Completion Report** | срез покрытия, результаты прогона, ссылка на отчёт Allure | отдельная страница, **не** раздел плана |
| **Test Incident Report** (дефект) | один дефект — один тикет | трекер задач |

**Четыре правила, без которых документ не принимается:**

1. **Критерии входа и выхода обязательны и измеримы.** «Покрыть API» — не критерий. Критерий: какие
   пути, на каком уровне тестирования, при каком результате считаем готовым.
2. **План и отчёт не смешивать.** План говорит, что собираемся делать; отчёт — что получилось. Цифры
   покрытия внутри плана превращают его в снимок, который через месяц врёт молча. Если цифры всё-таки
   в документе — рядом дата сверки и способ пересборки, лучше автоматической.
3. **Требования к разработчикам оформлять как критерии входа**, а не как просьбы. Нет спецификации,
   доступа, ключа, непривилегированного тестового аккаунта или изолированного контура — это
   невыполненный критерий входа: тестирование не начинается. Факт процесса, а не пожелание QA.
4. **Приоритет по риску, а не по порядку путей** (риск-ориентированное тестирование). По каждой
   области — последствие отказа и кого затрагивает. Без перевода в риск требования QA проигрывают
   приоритет продуктовым задачам.

**Терминология.** Тестовый базис, тест-условие, тест-кейс, тестовые данные, критерий выхода, дефект
(в документах — «дефект», не «баг»), уровень тестирования, тип тестирования. Не путать: **тест-план** —
документ проекта, **тест-стратегия** — организационный документ; в один файл не сливаются.

**Уровни тестирования — только канонические**, вместо самодельных «L1/L2/L3»:

| Уровень | Что это на практике |
|---|---|
| **Component** | изолированный модуль: без реального backend, без UI-дерева |
| **Component integration** | связка модулей внутри приложения (ViewModel + repository на тестовых дублях) |
| **System** | приложение или сервис целиком против стенда (UI на устройстве, API-сьют) |
| **System integration** | несколько сервисов вместе — шлюз, авторизация, шина; E2E через контур |
| **Acceptance** | приёмка: боевой вход, реальное оборудование, сценарии заказчика |

Где «L1/L2/L3» уже прижились — в project `CLAUDE.md` держать таблицу соответствия, в новых
документах писать канонический уровень.

**Типы тестирования:** functional · non-functional (performance, security, usability, compatibility) ·
structural (white-box) · change-related: **confirmation** (проверка фикса) и **regression**.
Маркеры прогона (`smoke`, `regression`, `e2e`, `security`) — допустимое сокращение, но `smoke` это
подмножество по цели, а не уровень; в документах уровень и тип называть словами.

**Дефект ≠ отказ ≠ ошибка** — в документах и тикетах не смешивать: **error** (действие человека) →
**defect** (изъян в коде или требовании) → **failure** (наблюдаемое расхождение с ожидаемым).
Описываем **failure** — что наблюдали, и **defect** — где корень, если установлен. «Тест упал» не
формулировка; формулировка — «наблюдался отказ: что именно разошлось с ожиданием».
**Severity и priority — разные шкалы:** влияние на систему против срочности для бизнеса; проставлять обе.

**Набор тестов выводится техникой, и техника называется.** Не «придумали кейсы», а: эквивалентное
разбиение · анализ граничных значений (фиксировать сами границы: min−1, min, min+1, max−1, max, max+1) ·
таблицы решений · переходы состояний · попарное тестирование · сценарии использования. White-box
(покрытие операторов и ветвей) — там, где тесты живут внутри сервиса. Experience-based (предугадывание
ошибок, исследовательское, чек-листы) — только как дополнение и с явной пометкой. В плане и в описании
сьюта указывать технику и почему её достаточно для покрытия риска.

**Ожидаемый результат формулируется до прогона**, а не подгоняется по факту наблюдения.

**Не документируем то, что уже автоматизировано.** Ручные тест-кейсы при наличии автотестов не ведём:
источник истины — код теста и отчёт Allure. Документ описывает объём, подход и границы, а не шаги.

## Приёмники результатов прогона — у каждого своя роль

Прогон уходит в два места, и они не заменяют друг друга:

| Приёмник | На какой вопрос отвечает |
|---|---|
| **Allure** | почему упало — шаги, вложения, скриншоты, тренды |
| **Система тест-менеджмента** (плагин трекера) | что покрыто и готово ли к релизу: требование → тест → прогон → дефект |

- **Тест-задачи создаёт импорт результатов, руками их не ведут.** Правило «не документируем то, что
  уже автоматизировано» действует и здесь: тест-кейсы в трекере не пишем, там появляются
  автосозданные Test-задачи от импорта.
- **Ручные тест-кейсы — только для неавтоматизируемого:** финальная приёмка, вход в боевой контур,
  реальное оборудование, полевые проверки.
- **Окружение передаётся при импорте** (`prod`, `dev`, `<стенд>`, `device`) — это свободные строки,
  а не справочник: разнобой написаний расколет историю прогонов на несвязанные ветки.
- **Статус Test-задачи в трекере не отражает результат** — результат живёт в прогоне (Test Run)
  внутри плагина. Типы тест-менеджмента исключать из фильтров досок, иначе тесты забивают бэклог.
- Сопоставление повторных прогонов идёт по идентификатору теста (полное имя метода/определение) —
  **переименование теста порождает новую Test-задачу** и обрывает историю. Переименовывать осознанно.

## LLM-Wiki — база знаний проекта

Знания о коде агент ведёт не в чатах, а в markdown-вики (паттерн Карпатого): код — неизменяемая
истина, вики — накапливаемый слой знаний по явной схеме.

- Два дерева по назначению: **рабочий слой** (планы, задачи, аудиты, отчёты — внутреннее) и
  **export-слой** (описание системы для коллег, выгружается в трекер/доки). Граница назначения =
  граница дерева; export не ссылается на рабочий слой.
- У каждого проекта — `index.md` (каталог заметок, one-line summary) и `log.md` (append-only
  хроника, ops: ingest / query / lint / scaffold).
- Операции: **ingest** (источник → страницы → index → log) · **query** (ответ из вики со ссылками) ·
  **lint** (битые ссылки, сироты, дрейф, противоречия).
- Ценность копится: каждая новая заметка перелинковывается с накопленным.
- **Хронику не переписываем.** Датированная запись — снимок момента; устаревший факт закрывается
  **новой** записью, а не правкой старой. Отменённое направление помечается статусом (`dropped`)
  вместе со связанными заметками, а не стирается: удалённая история возвращается как повторно
  задаваемый вопрос.
- **Достоверность видна у каждого факта.** В описании системы помечать, откуда он взят:
  подтверждено кодом или измерением · взято из унаследованного источника и не проверено ·
  чёрный ящик. Схема, где догадка неотличима от факта, вреднее отсутствия схемы;
  у источника указывать его дату.
- **Диаграммы проверять машинно.** Схема-как-код (mermaid и подобное) валидируется парсером,
  а не просмотром: невалидный блок молча не отрендерится в вики или выгрузке.
- **Документацию не плодим в репозитории кода.** Описания сервисов, планы, аудиты, баг-репорты,
  заметки и session-логи живут в базе знаний, а не в `.md`-файлах рядом с кодом. Исключения ровно
  два: `.md`, уже трекаемый в git как кодовый deliverable (проектный instructions-файл, README),
  и gitignored `./HANDOFF.md`.

> Конкретные пути дерева и инструмент (Obsidian или иной) — в личной/командной настройке;
> здесь — принцип.

## Handoff — передача контекста между сессиями/людьми

Handoff привязан к **ветке** (линии работы), а не к рабочему дереву: переключение ветки или
повторный clone не должны обнулять контекст.

- `./HANDOFF.md` в репозитории — **gitignored** ephemeral-кэш «возобновись здесь»
  (нет в `.gitignore` — добавить).
- Durable-копия — в базе знаний участника, **отдельная заметка на ветку** (слаг ветки: `/` → `--`,
  напр. `feature/x` → `feature--x`). Она источник истины и переживает `git clean` и смену ветки.
  Заводить только для ветки = реальной линии работы; после merge переводить в `status: done`,
  а не удалять.
- **На возобновлении сверять ветку:** ветка в шапке `./HANDOFF.md` ≠ текущей (или файла нет) →
  читать durable-копию по слагу текущей ветки, а не доверять устаревшему локальному кэшу.
- В handoff: что сделано, что осталось, ключевые `file:line`, failed approaches, как проверить.
