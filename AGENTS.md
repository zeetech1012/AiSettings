# Правила работы AI-агента

> Единственный файл правил. Локально он лежит в `~/.agents/AGENTS.md`, а `~/.claude/CLAUDE.md`
> и `~/.codex/AGENTS.md` ссылаются на него symlink'ами. `scripts/aisettings.py` экспортирует
> этот файл в нативный файл инструкций каждого клиента, пути заданы в `config/clients.json`.
> Секретов, внутренних адресов и личных путей здесь нет: их каждый держит у себя.

## Роль агента

Роль задаётся в начале твоего локального файла, над правилами. Она описывает уровень экспертизы,
специализацию, стиль ответа, язык объяснений и кода и то, что агент отмечает до реализации.
Образец:

```
You are acting as a **Senior QA Engineer / Software Architect**.
- Give expert-level advice, skip basic definitions
- Respond in <язык> for explanations, keep code and technical terms in English
- Skip polite openings and closings, go straight to the point
- If a proposed solution risks flaky tests or poor maintainability, flag it explicitly
```

Всё ниже передаётся без изменений.

## Дефекты и задачи

- Найденный дефект оформляется **одним** тикетом: корень, воспроизведение, предлагаемый подход.
  Разработчику этого достаточно. Тикеты-обёртки («реализовать исправление дефекта X») не заводятся.
- Перед созданием тикета проверяются дубли: открытые тикеты и список дефектов в вики
  (полнотекстовый поиск трекера ненадёжен). После transient-ошибки create проверить,
  не создался ли тикет.
- QA не правит production-код. Тест, воспроизводящий дефект, остаётся красным до исправления.
- Задача создаёт свой артефакт или изменение системы. Встречи живут в календаре. Контроль
  чужой проверки становится критерием приёмки той задачи, которая создаёт проверяемый объект.
- **Трекер и планирование разделены.** В трекер попадает то, что кто-то будет делать: дефекты,
  задачи, запросы на изменение. Карты планирования, открытые вопросы и решения в работе живут
  в вики и ссылаются на тикеты. На доске они лежали бы мёртвым грузом.
- В тикете описывается failure (что наблюдали) и defect (корень, если установлен).
  Severity и priority — разные шкалы; в трекере ставится priority.

## Параллельные сессии

Над базой знаний, трекером и общими каталогами могут работать несколько сессий агента сразу.

- Свои временные файлы держи в scratchpad сессии. В общий каталог пиши, проверив, что по пути
  нет чужого файла.
- У раздела правил или skill один ведущий. Перед правкой общего файла найди соседние сессии
  и предупреди их; остальные передают ведущему факты, а не правят сами.
- Перед записью перечитай файл и вставляй по якорю, который встречается ровно один раз.
  После записи сообщи, что файл свободен.

## Маршрутизация по стекам

| Репозиторий | Стек | Заметки |
|---|---|---|
| `energy-app-native` | Kotlin (KMP + Compose, JUnit 5 + compose-test) + Swift/XCUITest (iOS) + Allure | уровни component и component integration на общем коде, system на устройстве; локаторы через единый `testTag`-контракт |
| `qa-monorepo` | Python: pytest + httpx + pydantic v2 + allure-pytest | backend black-box: API, контракты, E2E над HTTP, WS, AMQP; уровень и тип теста задают маркеры pytest, а не каталог |
| `auth_http` и другие Go-сервисы | Go: `net/http`, `httptest`, `testing`/testify, table-driven | white-box, тесты в репозитории сервиса |

По умолчанию: бэкенд, контракт и оборудование → Python/pytest (`qa-monorepo`); экран или Compose →
Kotlin (KMP); специфика iOS (клавиатура, secure-field, permissions) → Swift/XCUITest. Если неясно,
спроси. **Файл инструкций самого репозитория главнее этого файла.**

## Как писать код

1. **Думай до кода.** Назови допущения. Если трактовок несколько, покажи их, а не выбирай молча.
   Есть путь проще — скажи. Неясно — остановись и спроси.
2. **Простота.** Минимум кода под задачу: без спекулятивных фич, абстракций для одноразового
   кода и конфигурируемости, которую не просили.
3. **Хирургические правки.** Трогай только нужное, соседний код не «улучшай», стиль файла важнее
   твоих предпочтений. Убирай только мусор, который оставила твоя же правка. Каждая изменённая
   строка прослеживается к просьбе.
4. **Критерий успеха до кода.** «Почини дефект» превращается в «тест воспроизводит дефект,
   затем становится зелёным». Сформулируй план «шаг → проверка» и иди до подтверждённого результата.
5. Код полный и запускаемый, без заглушек «implement this». Порядок в файле: imports →
   fixtures и helpers → tests. Файл длиннее ~100 строк делится.

## Правила качества (все стеки)

- Один класс или функция отвечает за одно.
- URL, учётные данные и ID берутся только из ENV, фикстур или `BuildConfig`.
- Ожидание — polling или wait фреймворка с таймаутом. `Thread.sleep`, `delay`, `time.Sleep`,
  `time.sleep` запрещены.
- Тесты независимы: без общего изменяемого состояния и зависимости от порядка.
- Flaky-тест сломан. Retry и xfail его не чинят.
- Локаторы стабильные (`data-testid`, `testTag`), не XPath, CSS-класс или `R.id`.
- Каждый тест размечен для Allure (title и severity, epic/feature/story) и построен по
  Arrange-Act-Assert с шагами. Ответы API и скриншоты прикладываются, чтобы отчёт понимал
  не только разработчик.
- Python: `with allure.step("…")` простым текстом, без Given/When/Then; шаг верхнего уровня равен
  шагу ручного тест-кейса в системе тест-менеджмента. Kotlin: `allureStep("When: …")`.
- Cucumber runtime и `.feature`-файлы не вводятся. Gherkin допустим только как выходной артефакт
  прогона для импорта в систему тест-менеджмента; источник истины — код и Allure.
- Ручной шаг тест-кейса: Action — что сделать, с глагола; Data — что нужно; Expected Result —
  что должно получиться. Проверку в одно действие не дробить. Адресов, имён стендов и секретов
  в шагах нет, их подставляет исполнитель.

## Чек-лист ревью

Агент отмечает автоматически:

- sleep-ожидание → flaky-риск;
- URL или учётные данные в коде → нарушение правила ENV;
- нет разметки Allure → отчёт неполон;
- XPath или CSS-локатор → хрупкий селектор;
- фикстура с неверным scope → нарушена изоляция;
- общее изменяемое состояние → тесты зависят от порядка;
- несколько логических проверок без шагов → падение трудно разобрать;
- перезапись существующего тестового дубля (`cat >` поверх `Fake*`) → ломаются чужие тесты;
- процент покрытия без знаменателя → цифра ничего не говорит.

**Покрытие** называется вместе с контуром (что исключено из знаменателя) и командой пересборки;
фильтры живут в конфиге сборки. Сравниваются только срезы с одним знаменателем. Репозитории
проверяются поверх HTTP-мока, экраны — поверх дублей уровня репозитория; уровни не смешиваются.

При диагностике (flaky, красный тест, триаж) первой проверяется гипотеза с наименьшим числом
допущений, которая сходится с фактами (skill `occams-razor`).

## Документация сервисов и тестовый базис

- Ожидаемый результат берётся из требований (ФТ, ТТ) или контракта, подтверждённого владельцем.
  Реализация не служит оракулом теста: ожидание, списанное с кода, проверяет код сам на себя.
- До тест-дизайна прочитай описание сервиса, контракт и требования целиком.
- ФТ утверждает владелец продукта, ТТ — технический владелец, QA проверяет однозначность
  и проверяемость. Каждое требование подтверждается отдельно: согласующий, дата, версия
  страницы, ссылка на решение. Изменение смысла требует повторного согласования; ID не меняется
  и не используется повторно.
- Код читается, чтобы снять форму интерфейса (пути, поля) и найти состояние, которое меняет
  проверка. Факт из кода помечается 🟡 с `file:line`; контракт остаётся `status: draft` до
  подтверждения владельцем. Дефекты по чтению кода не ищутся.
- Поведения нет в документации — это вопрос владельцу или невыполненный критерий входа.
  Ожидание из кода не выводится. Нет контракта — сними форму черновиком через `service-doc`,
  пути не выдумывай.
- Дефект заводится по отказу, наблюдаемому в прогоне. Расхождение утверждённого требования
  с реализацией — дефект кода, воспроизводящий тест остаётся красным. Расхождение черновика
  с кодом — дефект черновика.
- Описание сервиса живёт в export-слое базы знаний, OpenAPI и AsyncAPI публикуются оттуда.
  Каноничный файл для CI хранит владелец сервиса по пути, указанному в заметке.

## Тестовая документация: ISO/IEC/IEEE 29119-3, словарь ISTQB

Ведутся **четыре** типа документов, остальные типы стандарта заводятся только при реальной нужде.

| Тип по 29119-3 | Содержание | Где живёт |
|---|---|---|
| **Test Plan** | объём, подход, уровни, критерии входа и выхода, риски, окружение, раздел «что не тестируем и почему» | export-слой вики → корпоративная вики |
| **Test Environment Requirements** | контуры, доступы, ключи, гейты небезопасных операций, изолированный стенд | раздел плана |
| **Test Status / Completion Report** | срез покрытия, результаты прогона, ссылка на отчёт Allure | отдельная страница, **не** раздел плана |
| **Test Incident Report** (дефект) | один дефект — один тикет | трекер задач |

Документ не принимается без четырёх правил:

1. **Критерии входа и выхода измеримы.** «Покрыть API» — не критерий. Критерий называет пути,
   уровень тестирования и результат, при котором работа готова.
2. **План и отчёт не смешиваются.** План говорит, что собираемся делать, отчёт — что получилось.
   Цифры покрытия в плане через месяц устаревают без предупреждения. Если цифры есть,
   рядом стоят дата сверки и команда пересборки.
3. **Требования к разработчикам оформляются критериями входа.** Нет спецификации, доступа,
   ключа, непривилегированного тестового аккаунта или изолированного контура — тестирование
   не начинается.
4. **Приоритет по риску.** По каждой области указаны последствие отказа и кого оно затрагивает.
   Без этого требования QA проигрывают продуктовым задачам.

**Терминология.** Тестовый базис, тест-условие, тест-кейс, тестовые данные, критерий выхода,
дефект (не «баг»), уровень тестирования, тип тестирования. Тест-план — документ проекта,
тест-стратегия — документ организации; в один файл они не сливаются.

**Уровни тестирования** только канонические, вместо самодельных «L1/L2/L3»:

| Уровень | Содержание |
|---|---|
| **Component** | изолированный модуль: без реального backend и UI-дерева |
| **Component integration** | связка модулей внутри приложения (ViewModel + repository на тестовых дублях) |
| **System** | приложение или сервис целиком против стенда (UI на устройстве, набор API-тестов) |
| **System integration** | несколько сервисов вместе (шлюз, авторизация, шина); E2E через контур |
| **Acceptance** | приёмка: вход в производственный контур, реальное оборудование, сценарии заказчика |

Где «L1/L2/L3» уже прижились, project-файл инструкций держит таблицу соответствия, а новые
документы называют канонический уровень.

**Типы тестирования:** functional · non-functional (performance, security, usability, compatibility) ·
structural (white-box) · change-related: **confirmation** (проверка исправления) и **regression**.
Маркеры прогона (`smoke`, `regression`, `e2e`, `security`) допустимы как сокращение. `smoke` — это
подмножество по цели, а не уровень; в документах уровень и тип называются словами.

**Error → defect → failure** не смешиваются: error — действие человека, defect — изъян в коде или
требовании, failure — наблюдаемое расхождение с ожидаемым. «Тест упал» — не формулировка.
Формулировка: «наблюдался отказ», и что именно разошлось с ожиданием.

**Набор тестов выводится техникой, и техника называется:** эквивалентное разбиение · граничные
значения (min−1, min, min+1, max−1, max, max+1) · таблицы решений · переходы состояний ·
попарное тестирование · сценарии использования. White-box (покрытие операторов и ветвей) —
там, где тесты живут внутри сервиса. Experience-based техники (предугадывание ошибок,
исследовательское тестирование, чек-листы) — только дополнение, с пометкой. План называет
технику и объясняет, почему её хватает на риск.

**Ожидаемый результат формулируется до прогона.**

**Проектирование не ждёт окружения.** Нет стенда или доступа — блокируется прогон, а не дизайн.
Автоматизируемое пишется заранее под гейтом, неавтоматизируемое — шагами. «Писать нечего»
только тогда, когда неизвестен ожидаемый результат; это вопрос владельцу.

- Порядок изменяющей проверки: гейт `ALLOW_*` → данные профиля → снимок состояния → действие →
  проверка → восстановление в `finally`. Выключенный гейт даёт честный пропуск, а не отказ
  по незаполненной переменной.
- Деструктивное действие выполняется только над расходуемым объектом из профиля окружения.
- Значение, которого нет в исходниках проверяемой версии, помечается 🟡 и подтверждается
  первым прогоном.

**Автоматизированное не документируется повторно.** Ручные тест-кейсы при наличии автотестов
не ведутся: источник истины — код теста и отчёт Allure. Документ описывает объём, подход и границы.

## Приёмники результатов прогона

Прогон уходит в два места, и они не заменяют друг друга:

| Приёмник | На какой вопрос отвечает |
|---|---|
| **Allure** | почему упало: шаги, вложения, скриншоты, тренды |
| **Система тест-менеджмента** (плагин трекера) | что покрыто и готово ли к релизу: требование → тест → прогон → дефект |

- **Тест-кейсы автотестов создаёт импорт результатов**, вручную их не ведут.
- **Ручные тест-кейсы — только для неавтоматизируемого:** приёмка, вход в производственный
  контур, реальное оборудование, полевые проверки. Ручной кейс без шагов считается незаведённым.
- **Окружение при импорте** передаётся строкой (`prod`, `staging`, `test`, `device`). Это свободные
  строки, а не справочник: разные написания расколют историю прогонов.
- **Статус тест-задачи в трекере не отражает результат**, результат живёт в прогоне внутри плагина.
  Типы тест-менеджмента исключаются из фильтров досок, иначе тесты забивают бэклог.
- Повторные прогоны сопоставляются по идентификатору теста (полное имя метода), поэтому
  **переименование теста создаёт новый тест-кейс** и обрывает историю. Переименовывай осознанно.
- Успешный импорт не означает доставку: после импорта сверь число прогонов чтением.

## Массовая правка трекера, вики и тест-менеджмента — скриптом

Запись во внешние системы готовится скриптом. Запускает его владелец или агент по прямой просьбе
в текущем сообщении; общего «даю апрув» недостаточно. Скрипт обязан:

1. `--dry`: печатать, что запишет, ничего не отправляя;
2. защищать от повтора: читать состояние и отказываться, если правка уже нанесена;
3. проверять чтением: после записи перечитать объекты и напечатать `ok=N fail=0`.

Данные правки лежат отдельным TSV или JSON. Массовые правки задач идут с `notifyUsers=false`.

## LLM-Wiki: база знаний проекта

Знания о коде агент ведёт в markdown-вики, а не в чатах (паттерн Карпатого). Код остаётся
неизменяемой истиной, вики — накапливаемым слоем знаний по явной схеме.

- Два дерева по назначению: **рабочий слой** (планы, задачи, аудиты, отчёты) и **export-слой**
  (описание системы для коллег, выгружается в корпоративную вики). Export не ссылается на рабочий слой.
- У каждого проекта есть `index.md` (каталог заметок с однострочным описанием) и `log.md`
  (append-only хроника операций ingest, query, lint, scaffold).
- Операции: **ingest** (источник → страницы → index → log) · **query** (ответ из вики со ссылками) ·
  **lint** (битые ссылки, сироты, дрейф, противоречия).
- Новая заметка связывается ссылками с существующими.
- **Хроника не переписывается.** Датированная запись фиксирует момент; устаревший факт закрывает
  **новая** запись. Отменённое направление получает статус `dropped` вместе со связанными
  заметками и не удаляется, иначе тот же вопрос зададут снова.
- **У каждого факта видна достоверность:** подтверждено кодом или измерением · взято из
  унаследованного источника и не проверено · чёрный ящик. У источника указывается дата.
- **Диаграммы проверяются парсером.** Невалидный mermaid-блок не отрендерится в вики или выгрузке,
  и никто этого не заметит.
- **Документация не хранится в репозитории кода.** Описания сервисов, планы, аудиты,
  отчёты о дефектах, заметки и логи сессий живут в базе знаний. Исключения: `.md`, уже
  отслеживаемый в git как часть кода (project-файл инструкций, README), и gitignored `./HANDOFF.md`.

> Пути деревьев и инструмент (Obsidian или другой) задаются в локальной настройке.

## Handoff: один файл в каталоге проекта

- `handoff-create` пишет `./HANDOFF.md`, `handoff-resume` читает его оттуда и сверяет ветку.
- Новый handoff заменяет прежний. Копий в базе знаний и записей в `index.md` и `log.md` нет.
- `HANDOFF.md` не коммитится; если его нет в `.gitignore`, добавь.
- В handoff: что сделано, что осталось, неудачные подходы, ключевые пути и способ проверки.
- Когда контекст заполнен больше чем на 85%, предупреди пользователя и сохрани handoff.
  Если точного показателя нет, назови оценку приблизительной.

## Инструменты агента

- Повторяемые процедуры выполняются через skills (`service-doc`, `service-issue`, `doc-sync`,
  `occams-razor`, `handoff-create` и другие). Если задача совпадает с описанием skill, вызови его.
- Незнакомый репозиторий исследуют sub-agents `project-researcher`, `go-service-explorer`,
  `frontend-contract-miner`, если клиент их поддерживает. Перед правкой оцени последствия
  через MCP `codegraph`.
- Документацию библиотек бери из MCP `context7`, а не по памяти о версиях API.
